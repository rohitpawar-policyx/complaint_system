==================================================
ARCHITECTURE RULES
==================================================

1. Keep feature-specific code inside its feature.

2. Do NOT force every feature to contain:
   Form + API + Service + CSS + JS.

Only create files that are actually required.

For example, a simple feature may contain:

reasons/
├── reasonList.php
├── reasonForm.php
├── reasonService.php
└── reason.css

If JavaScript is not required, do not create a JS file.

If a separate API/request-handler is unnecessary, do not create one.

3. If code is reusable by multiple features, move it into app/shared/.

4. Keep database connection centralized in:

config/database.php

Do not create duplicate database connection files.

5. Use PDO and prepared statements everywhere.

6. Never concatenate user input into SQL.

7. Keep presentation separate from business/database logic.

8. Forms/views should primarily contain presentation.

9. Request handlers should handle HTTP input/output.

10. Services should contain business logic and database operations when a service layer is useful.

11. Do not over-engineer simple features.

12. Passwords must use:
password_hash()
password_verify()

13. Use PHP sessions for authentication.

14. Regenerate session ID after successful login.

15. Authentication and authorization are separate.

Authentication:
"Who is this user?"

Authorization:
"What can this user do?"

16. User status and role are separate.

User status:
- pending
- approved
- blocked

17. Never allow the frontend to choose or modify:
- user_id
- role
- account status
- complaint priority
- complaint ownership
- performed_by

18. Complaint priority must be calculated SERVER-SIDE from the selected complaint reason.

19. Complaint history must be an audit trail.

20. Multiple attachments are supported.

21. Uploaded files must be validated server-side.

22. Use htmlspecialchars() when displaying user-controlled data.

23. Use CSRF protection for state-changing requests.

24. Use reusable authorization/middleware rather than duplicating checks everywhere.

25. Common UI behavior belongs in assets/js/main.js.

26. Common CSS belongs in assets/css/main.css.

27. Feature-specific CSS/JS belongs to that feature only when needed.

28. Do not use inline CSS.

29. Do not use inline JavaScript unless absolutely necessary.

30. SweetAlert should be centralized/reusable rather than duplicated throughout the application.

==================================================
IMPORTANT COMPLAINT RULE
==================================================

The user selects a reason.

Example:

Policy Violation → HIGH
General Inquiry → LOW
Documentation Issue → MEDIUM

The frontend must NOT submit priority.

Server flow:

reason_id
↓
load reason from database
↓
read priority from database
↓
create complaint with that priority

Never trust frontend priority.
